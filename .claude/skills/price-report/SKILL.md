# 요금 제보 확인·반영 (탕방)

사용자가 사이트에서 보낸 제보는 **단서**다. 화면에는 근거를 확인한 값만 올린다. 이 절차는 읽기 → 확인 → 제안 → (승인) → 반영 → 상태 갱신 순서로 간다.

- **제보가 쌓이는 곳(2026-11-06부터)**: Cloudflare D1의 `reports` 표. 사이트 제보 창(`web/src/components/PriceReport`) → Worker `POST /api/report`(`worker/src/index.js` `postReport`)가 검사한 뒤 넣는다. 읽기·상태 바꾸기는 프로젝트 폴더에서 관리 도구로 한다(값·토큰은 출력되지 않는다).
  - 새 제보 보기: `node --env-file=.env scripts/d1_publish.mjs reports new` (`--json`을 붙이면 칸 전체)
  - 상태 바꾸기: `node --env-file=.env scripts/d1_publish.mjs report-set <번호> <상태> <검토 메모>`
  - 상태 값: `new`(새 제보) · `reviewed`(확인함, 반영 안 함) · `applied`(반영 완료) · `rejected`(반려)
- 제보 칸: 번호, 시각(UTC), 업체ID(`place_id`), 업체(`place_name`, 서버 목록 기준 이름), 성인 입장료(`adult`), 수건(`towel`), 세신(`scrub`), 확인 방법(`source`), 메모, 표시(`flags`), 수건 안내(`towel_info`), 드라이기(`hairdryer`), 세신 결제(`seshin_pay`), 상태, 검토 메모(`note`)
  (수건·세신은 **요금(원)**, 수건 안내·드라이기·세신 결제는 가기 전 걱정 정보(TOP 3)다. 제보는 요금만, 정보만, 둘 다 올 수 있다.)
- **예전 구글 시트**(`탕방 요금 제보`, 파일 ID `1yTWOx_VCJy5XtXvJDVm0LRioSpveg3YYIilUQgaDG_A`)는 2026-11-06 전 제보만 있다. 처음 이 절차를 D1로 돌릴 때 한 번, 시트에 상태가 '새 제보'인 줄이 남았는지 Google Drive 연결로 확인하고 남았으면 같은 방식으로 처리한다(시트 상태는 ego-browser로 고친다). 그 뒤로는 시트를 보지 않는다.
- 모드: `확인`이면 1~4단계까지만(읽고 정리해서 보여 주기). `반영`이면 이미 승인된 항목만 5~7단계. 인자가 없으면 1~4단계 뒤에 사용자 승인을 받고 5~7단계로 간다.

## 1. 읽기
1. `node --env-file=.env scripts/d1_publish.mjs reports new --json`으로 새 제보를 읽는다. 오류가 나면 `error.message`·`error.fix`를 그대로 사용자에게 알리고 멈춘다(토큰이 어긋나면 `fix-token`, 접속 불가면 인터넷 확인).
2. 읽은 건수를 조건과 함께 적는다. 예: "reports 표에서 상태 new인 제보 M건(최근 200건까지)".
3. 다음은 제외하고 개수를 알린다: 업체ID가 `TEST`이거나 업체/메모에 `[시험]`·`시험`이 든 제보(운영자 시험).
4. 새 제보가 없으면 "새 제보 없음"만 알리고 끝낸다.

## 2. 정리
업체별로 묶고, 제보마다 다음을 본다. 숫자는 코드로 센다.
- **표시 칸**: 이름 불일치 / 입장료·수건·세신 이상값 / 연락처 의심 / 업체 확인 못 함. 표시가 있으면 먼저 의심한다.
- **같은 값 제보 수**: 같은 업체·같은 값의 제보가 몇 건인지 코드로 센다. 참고만 한다(한 기기당 한 시간 5건 제한이 있어도 우회될 수 있다). 건수가 많다고 사실로 치지 않는다.
- **제보끼리 충돌**: 같은 업체에 값이 서로 다르면 모두 보여 준다.
- **지금 화면과 비교**: `web/public/data/onsen.json`의 해당 업체 `price`·`facts`와 비교한다(이미 확인된 값이 있으면 덮어쓰지 않는다. 더 강한 근거가 있을 때만 바꾸자고 제안한다).
- **업체ID 열쇠**: 카카오ID가 없는 곳(업체ID가 `lic…`로 시작, 98곳)도 `lic…` 값이 그대로 `onsen_prices.csv`·`place_facts.json`의 열쇠(카카오ID 칸)로 쓰인다(`export_web_data`가 같은 칸으로 찾는다). 시트의 업체ID를 그대로 열쇠로 쓰면 된다. 열쇠가 아예 비어 있는 2곳만 줄 번호(`m…`)라 반영하지 않고 "반영 불가"로 알린다.

## 3. 근거 확인 (제보만으로는 반영하지 않는다)
Claude가 **직접 볼 수 있는 근거**로만 확인한다.
- 이미 모은 자료: `data/collected/naver_places.csv`, 수집기 출력(`C:\Users\user\naver-crawl\out*/`), `data/curated/*`.
- 네이버 플레이스 가격표·사진, 업체 공식 홈페이지, 공공데이터(착한가격업소 등). 브라우저가 필요하면 ego-browser를 쓴다. 2차 수집이 돌고 있으면(`run-all2`/`collect2` 프로세스) 그 작업과 겹치지 않게 사용자에게 알리고 기다린다.
- **전화 확인은 제안하지도 넘기지도 않는다.** 근거를 못 찾으면 "확인 못 함"과 어디까지 찾아봤는지를 보고한다.

제보별 판정은 셋 중 하나다.
| 판정 | 뜻 | 제보 상태 |
|---|---|---|
| 일치 | 근거가 제보 값과 같다 | `applied`(반영 완료, 반영 뒤) |
| 불일치 | 근거가 제보 값과 다르다(또는 스팸·잘못된 제보) | `rejected`(반려, 근거 값이 이미 있으면 그 값을 유지) |
| 확인 못 함 | 근거를 찾지 못했다 | `reviewed`(확인함, 단서로 남김, 반영 안 함) |

## 4. 제안 (여기서 멈추고 승인 받기)
업체별 표로 보여 준다: 업체 · 제보 값 · 근거와 출처 · 판정 · 반영할 값 · 바꿀 상태와 검토 메모(한 줄). 일치 건만 "반영 제안"으로 묶는다. **사용자가 승인한 항목만** 5단계로 간다. 승인이 없으면 파일을 하나도 고치지 않는다.

## 5. 반영 (승인된 일치 건만)
- 입장료·수건·주차 가격 → `data/curated/onsen_prices.csv`의 해당 카카오ID 줄(없으면 새 줄). 칸: 카카오ID, 성인_평일, 성인_주말, 수건, 주차, 어린이, 추가요금_없음확인, 메모, 출처, 확인일. 출처에는 **제보가 아니라 확인한 근거**(예: 네이버 플레이스 가격표)를 적고, 확인일은 오늘(KST).
- 세신 금액·수건 정책·드라이기·**세신 결제** → `data/curated/place_facts.json`(제보의 수건 안내 `무제한/1장/2장/3장 이상`은 `towel`의 `mode`·`count`로, 드라이기는 `여탕 유료 · 남탕 무료`처럼 탕별로 오며 `hairdryer.women`·`hairdryer.men`의 `paid`(무료·유료)·`none: true`(없음)로, 탕 구분 없는 예전 제보 `무료/유료`는 `hairdryer.paid`로, 세신 결제 `현금만/카드 가능`은 `seshin.payment`의 `cash_only/card_ok`로 옮긴다. 남탕·여탕이 다르다는 메모가 있으면 성별을 나눠 적는다. 근거를 확인한 것만)의 `places[카카오ID]`. 기존 모양(`seshin.price_full`, `towel.women/men`, `hairdryer.paid`·`hairdryer.women/men`, `checked`, `source`)을 따르고, **없는 칸은 적지 않는다**(추측 금지).
- 파일 인코딩은 `utf-8-sig`(BOM 포함), CSV는 번호 칸 없이 쓴다. 기존 줄 모양(따옴표·줄 끝)을 그대로 따른다.
- 이어서 `cargo run --release --bin export_web_data`로 화면 데이터를 다시 만들고, 반영 전후의 확인된 요금 업체 수를 조건과 함께 비교해 보여 준다. 그다음 `web`에서 `npm run build`가 통과하는지 확인한다.
- **사용자 화면에 내보내기**: 데이터는 DB 공개본에서 나가므로, 사용자가 원하면 `d1_publish.mjs ingest` → `diff`로 바뀐 곳을 보여 주고, 사용자가 '공개'하라고 할 때만 `publish`한다(수집 프로그램 '서비스 공개' 카드로 해도 같다). 공개 전에는 사용자 화면이 바뀌지 않는다.
- **커밋·푸시는 사용자가 말할 때만** 한다. 하기 전에 `git status`를 보여 주고 이번 작업과 관계없는 변경은 넣지 않는다.

## 6. 상태 갱신
승인된 판정대로 제보마다 `report-set <번호> <applied|rejected|reviewed> <검토 메모>`를 실행한다(검토 메모: 근거와 날짜를 한 줄로, 200자까지). 끝나면 `reports new`를 다시 읽어 처리한 번호가 빠졌는지 확인한다.

## 7. 마무리 보고
처리한 제보 수(반영 / 반려 / 확인함 / 반영 불가), 바뀐 파일, 다음에 할 일(확인 못 함 건의 추가 근거)을 짧게 적는다. Notion 기록은 사용자가 요청할 때만 남긴다.

## 지킬 것
- 제보 값을 근거 없이 화면 데이터에 넣지 않는다. 사람이 확인한 값만 `data/curated/`에 둔다.
- 개인 이름·전화번호는 어디에도 옮기지 않는다. 메모에 연락처가 있으면 Worker가 이미 `[연락처 의심, 가림]`으로 바꿔 저장한다. 제보자·접속 해시(`who`·`ip_hash`)는 관리 도구가 내보내지 않으며, 다른 방법으로 읽지도 옮기지도 않는다.
- 비밀 값(`.env`의 `TANGBANG_ADMIN_TOKEN`, 예전 `REPORT_SHEET_URL`·`REPORT_SHEET_SECRET`)은 열어 보지도, 출력하지도 않는다. `.env`는 `--env-file`로 넘기기만 한다.
- 숫자(개수·평균)는 코드로 계산하고 어떤 조건으로 셌는지 같이 적는다.
- 삭제는 사용자가 말했을 때만 한다. 제보는 지우지 않고 상태로만 관리한다.
